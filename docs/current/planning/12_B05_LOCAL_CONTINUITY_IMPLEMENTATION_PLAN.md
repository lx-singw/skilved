The founder's sprint loop permits independent local engineering while formal G2/source/user gates remain open. This plan does not activate a release, account, cloud sync, receipt intake or provider trial.

## Outcome and boundaries

A signed-out person can save a current public opportunity, leave, return and retain their own progress while seeing current source-backed facts. Save/remove/clear and stage changes must report the actual committed result. Missing or unsafe records cannot retain cached application links. Save data is local personal annotation; opening the issuer route and reporting Applied are separate events. Checklist ticks remain transient unless a separately reviewed extension is agreed; no document upload or personal notes field enters this scope.

Use a dedicated IndexedDB database, separate from theme/site settings and future receipt capabilities. One bounded versioned JSON document contains at most 100 entries: public ID, last viewed revision, saved/updated times, stage, last route-open time and applied-report time. Do not store source text, titles, destinations, contact details, documents or tokens for another service. Load current public facts on revisit. This is not encryption, a backup or a cross-device service.

## Concurrency and failure rules

All document mutations occur within one IndexedDB readwrite transaction. A caller's observed token must match the committed document before a save/remove/stage/route/revision action can write. Only transaction completion establishes success; request success can still be followed by abort. A conflict reloads and asks for a new explicit action rather than silently retrying an old snapshot. Tokens, not browser clocks, decide concurrency.

Clear is an explicit action over all progress currently in this database. It commits an empty document with a new token, including recovery from unreadable document data, so queued stale edits cannot restore old entries. Actual site-data/database deletion produces a missing document; a caller with an old token conflicts. A deliberate new save after observing empty state is allowed. UI effects, hydration, broadcasts and focus handlers must never replay a write. Keep database connections short and close on version changes; handle unavailable/blocked/error cases with a bounded response.

Older or future document versions are not automatically migrated or overwritten. Unknown/corrupt items do not crash the catalogue. The future UI must explain what cannot be read and offer scoped clear only after confirmation. A failure cannot claim durable removal/clear/save. Receipt access remains a separate database and separately explained control.
