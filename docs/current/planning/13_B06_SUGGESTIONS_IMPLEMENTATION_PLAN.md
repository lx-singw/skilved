## Outcome and audited starting point

A signed-out person submits a supported public notice URL without giving contact details, documents or a profile. They either receive a current approved public result or obtain private, expiring access to their own suggestion status and withdrawal. Another person suggesting the same URL must receive separate private access. A new suggestion never establishes authenticity, eligibility, source permission or a published listing.

At the B06-1 starting audit, the code had no suggestion/status/withdrawal endpoint, suggestion store, receipt store or suggestion contract. The current packet position below records delivered work. B04's incorrect-listing report queue is distinct and supplies no suggestion capability. Reuse B03's validated Source records, operator authorization/audit, guarded retrieval, approved public projection and explicit source-target policy. Keep its provider budgets and publication qualification holds. Reuse B05's transaction/failure lessons, while keeping receipt access in a separate database.

All six categories, both internship routes, broad jobs, free consumer access and later R0–R5/S01–S35 work remain in scope. The first implemented source adapters do not establish full inventory or remove any category.

## URL and source boundary

B06-1 accepts bounded ASCII-host HTTPS URLs with a canonical, unencoded path, rejects credentials, explicit ports/IP hosts, whitespace/control/backslashes, query/fragment, percent encoding, path parameters and parser-normalized-away segments. Only scheme/host normalization is allowed; do not strip an unknown parameter or fragment to manufacture a supposedly public URL. Some legitimate public URLs are deliberately unsupported by this initial syntax. Later reviewed source-specific parsing can admit necessary non-sensitive forms without widening arbitrary retrieval. The UI must explain this limitation and ask for a clean public notice link rather than claim that every rejected URL is malicious.

The classifier is private preflight, not permission or destination validation. A Source row must already be reviewed; actual source permission is an external fact. The queue stores the selected source revision, and the worker rechecks current permission/pause/URL policy immediately before work. Guarded retrieval still pins public DNS/socket addresses, validates TLS, revalidates every bounded redirect and enforces time/byte/MIME limits. Never pass a visitor's cookies/login, follow arbitrary employer links or turn an anonymous request into public worker authority.

An approved-result lookup uses current approved public provenance and canonical identity, not URL equality as proof of authenticity. One notice may contain multiple intakes: return the applicable bounded public results or ask for review; never choose the first unrelated intake or leak draft IDs. Unknown/new results remain private until explicit review/publication. Suggestion-origin work must stay review-only even if an independent source polling pipeline has another qualified publication mode.

## Receipt and idempotency protocol to implement in B06-2/3

Use a new random receipt ID and a 256-bit capability scoped to that receipt and operation family. No capability is a user identity or a permission to publish. Store its hash, key ID, expiry and revocation state privately. Compare hashes in constant time after fixed-format validation. GET/DELETE require Authorization header; public IDs, raw URL matches and a caller-supplied user ID cannot authorize access. Wrong, missing, expired and revoked credentials receive the same non-enumerating failure. Receipt responses expose status/revision/times and current approved public result IDs only; exclude raw submitted URL, source snapshots, operator notes, model output and other submitters.

Response loss must not force plaintext bearer storage. Selected design for implementation/testing: derive the capability with HMAC-SHA-256 from a dedicated high-entropy server key, a domain/version label, random receipt ID and random per-receipt nonce. Store only the derived token's hash plus the non-secret derivation metadata/key ID. Re-derivation supports an authorized idempotent create replay. No production default key; missing/invalid key material keeps intake unavailable. Keep an explicit bounded key ring for still-valid receipts; rotation/removal/revocation and response-loss behavior require tests before exposing a route. Test keys are synthetic; actual secrets remain outside Git and logs.

The first-party client generates a high-entropy idempotency key before sending and retains it privately for retry. Treat that key as a replay credential: header-only, hashed server storage, redacted from logs/analytics and never a public dedup identifier. Same key plus same normalized input replays the same receipt and capability within its validity; same key plus different input fails without mutation. Expired/revoked replay cannot revive access or extend expiry. Distinct keys for one public URL create distinct receipt IDs/capabilities while sharing only a private work key. No receipt sharing through a public URL hash. B06-2/3 must test the full concurrent and lost-response protocol, rather than counting this design text as security evidence.

## Persistence, workload and lifecycle

Use separate private collections for receipt records, hashed idempotency mappings, deduplicated review work and admission counters. Keep client database access denied; backend access stays behind existing authenticated operator or capability checks. Raw URLs exist only in the bounded private work record where needed; do not copy them into public result metadata, counters, outbox reasons or error logs. Use expected revisions and transactions for state/ref-count changes. Token issuance/replay cannot cause network/model work inside a database transaction.

Candidate engineering limits for emulator implementation: at most 100 pending review jobs, 500 active receipts, 50 create attempts per hour globally, 600 status reads per hour globally and one suggestion fetch/review work item at a time. Retried creates and status calls still consume their applicable admission budget. Enforce atomic limits and bounded indexed lookups; reject malformed/missing configuration rather than assuming unlimited capacity. These are conservative test defaults, not funded production capacity or a complete anonymous-abuse solution. Actual edge protections, supported workload and review coverage remain launch decisions. Existing source fetch cadence, byte/time bounds and provider budgets take precedence; this plan grants no new provider calls.

New requests may be disabled while existing authorized status/withdrawal remains available. Reviewer decisions require authenticated source-reviewer authority, expected revision and a bounded safe reason. Public resolution requires an actually approved current listing. Unsupported, paused and unresolved are honest outcomes, not hidden retries or successful publication. Do not promise a continuously staffed queue or guaranteed completion time.

Withdrawal immediately revokes that receipt's access and stops its unnecessary participation in work. Do not cancel another submitter's still-needed work or remove independently sourced public facts. Leased workers recheck cancellation/generation before persisting a result. Expiry similarly cannot keep orphaned work alive. Purge private URLs, receipt/idempotency data and queue material under the adopted purpose/retention schedule; retries must not resurrect deleted records. Review backup/deletion replay separately.

The [governance retention baselines](../governance/03_DATA_GOVERNANCE_AND_RETENTION.md) propose a 30-day capability maximum and resolution/withdrawal-based cleanup, with unresolved review/closure deadlines. They remain proposals requiring actual purpose/vendor/operating review and notice before live collection. B06 tests use explicit synthetic clocks/configuration and prove expiry/deletion mechanics; they do not establish legal adoption or actual processor deletion.

## API/UI and acceptance gates

POST /api/v1/opportunity-suggestions accepts JSON URL only with a bounded idempotency header. GET /api/v1/opportunity-suggestions/{id}/status and DELETE /api/v1/opportunity-suggestions/{id} use header-only capabilities. Reviewer resolution remains a separately authenticated admin operation. Bound body bytes/read time, header lengths, queue work and status projections; errors contain stable codes, not submitted values or raw exceptions. Private responses/pages use no-store/no-referrer and no indexing. Do not enable broad credentialed CORS or cookie-based receipt access. Document the exact disabled behavior in tests.

The form requests no email, phone, screenshot, application credentials or documents. Before submit, explain supported public links, review uncertainty, local anonymous access/loss and withdrawal versus independently sourced records. Store only receipt access material/expiry and necessary retry state locally in a dedicated database. Confirm local storage only after commit; do not claim a server submission failed solely because storing its receipt failed. Never put a capability or raw suggestion into a navigation/share URL, public formatter, analytics or metadata. A lost-access state cannot be recovered by guessing a person's identity.

Completion evidence must include adversarial URL/parser/network tests; persisted capability ownership, replay, expiry and redaction; queue/cancellation/deletion concurrency; default-disabled HTTP boundary; actual browser end-to-end status/withdrawal/local loss; current-source qualification, real review coverage/retention notice, participant/device results and eventual deployment/release authority. Until those actual gates pass, report scoped local evidence and keep intake disabled. Independent B07 public-export work may progress under the founder's loop while external acceptance remains explicitly open.
