# Authenticated suggestion review and current status

16 October 2026. B06-5a advances the [suggestions plan](../planning/13_B06_SUGGESTIONS_IMPLEMENTATION_PLAN.md) after [runtime/routes](94_SUGGESTION_RUNTIME_ROUTES_AND_EMULATOR_HTTP_2026-10-16.md). It adds local reviewer operations and current public-result status. Intake remains default disabled and DELETE remains unavailable. Full B06 and formal M0 acceptance remain open.

## Implemented boundary

`SuggestionReview` uses `Catalogue.identity`, the transaction-current active `source` role and `Catalogue.mutate`. A general reviewer role alone cannot decide suggestions. The strict command contains a work ID, expected work revision, outcome and at most 20 unique public IDs; free text, notes, URLs and an audit actor are rejected. Audit action/subject/verified actor/time and fixed outcome reason are the only audit fields. Source URLs remain in private work and authenticated queue output, never in audit reasons or submitter status.

Work supports pending, reviewing, resolved_to_listing, unresolved, unsupported and paused states. Pending/reviewing may receive an outcome; a completed or paused outcome requires an explicit reviewing transition before another decision. A repeated/stale decision conflicts without another audit. Expected work revision also detects concurrent admission. New submitters inherit the current nonresolved outcome without starting another review; a stale resolved work item cannot issue new review access. Existing receipt retries remain immutable and recoverable. Current approved-result create shortcuts keep their existing semantics.

One transaction validates the bounded physical inventory, current source policy when starting/resolving, and every changed receipt before writing. It changes the work and all its unexpired/unrevoked receipts together, preserving capabilities, expiry, reference counts and global capacity. Expired/revoked receipts remain unchanged. Work with no eligible receipt cannot be reviewed. All retained documents still consume physical slots; this packet does not reclaim slots or implement withdrawal. Schema defaults admit previous pending records without result IDs; resolved records require unique nonempty IDs. Corrupt IDs, accounting, states, future update times and revision overflow fail closed.

Resolution requires the complete current set of canonical, approved, provenance-matched public IDs for that notice, using the existing approved-result guard. It does not publish or modify public facts. Source checks inspect the entire bounded registry, including overlapping registrations, current revision, permission fingerprint, pause and category scope. This is enforcement of configured policy, not evidence of real permission.

Every resolved receipt read rechecks current work, current registry and current public/private approval, exact snapshot provenance, freshness and aliases. It returns only the intersection of reviewer-selected IDs and current approved IDs. Removed, withheld, stale or hidden originals are omitted; no remaining IDs produces `unresolved` with an empty array. A new canonical/other intake is never silently substituted. Closed approved listings remain valid public results. Missing/corrupt work or source fails unavailable; invalid capabilities still fail before these reads with the same nonenumerating not-found response. Status reads do not rewrite the receipt or audit: its revision/times describe the persisted review decision, while current link availability may change independently.

The local operator CLI adds `suggestion-queue` and `suggestion-review`, behind explicit trusted suggestion/base configuration. Intake may be off while reviewing existing work. Queue output has bounded work summaries for authenticated operators and excludes receipt IDs, capability/hash/nonce, key material and reference counts. Tokens stay in the existing private token file. No public reviewer route, publication, worker lease, retrieval or model call is added.

## Verification

Final checks pass: 37 contracts/build, 24 focused runtime/config/HTTP/crypto/policy cases, 51 combined actual emulator cases (15 new reviewer cases plus 36 existing domain/HTTP cases), 90 web tests, lint, typecheck and fresh production build. No cases are skipped. The actual Next HTTP journey now checks receipt resolution, removes current public results, returns unresolved without stale IDs and retains that exact status after server restart with intake off. Operator help also passes. No browser persistence/device/user or production observation is inferred. Private commands, initial failures, final logs and input hashes are retained under ignored `.artifacts/sprint-loop/b06-review-2026-10-16/`.

The initial combined run passed 48 of 50 tests. Its two failures were test assumptions: anonymous REST Auth signup issued a token for the CLI project rather than the isolated Firestore fixture project; concurrent admission could advance the work revision before both expected-revision reviewers. One targeted correction binds the synthetic Auth verifier to the actual token audience and tests concurrent review and admission, with a separate two-reviewer one-winner assertion. Production authorization guards and acceptance criteria remain intact. Review also adds complete-registry ambiguity and actual HTTP resolved/removal checks.

The Auth case exercises the actual local Auth emulator and Admin token verifier, with role/receipt data in a separate fixed Firestore fixture project. This proves the local verifier/role path, not deployed project/IAM binding or live identity operations. The 500-reference case exercises an actual emulator transaction; it is not a production load/cost qualification. Firestore's [transaction documentation](https://firebase.google.com/docs/firestore/manage-data/transactions) requires reads before writes, and its [quota documentation](https://firebase.google.com/docs/firestore/quotas) bounds transaction request size; this implementation keeps explicit application-level inventory limits.
