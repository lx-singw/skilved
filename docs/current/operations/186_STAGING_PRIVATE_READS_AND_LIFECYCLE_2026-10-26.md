# Staging private reads and publication lifecycle

26 October 2026 (SAST). The staging web service account has now read the persistent catalogue through the normal HTTP handler: an empty feed and 404 for all five private drafts. Its attempted Firestore create was denied. All 422 database documents remain unchanged. Hosting and production publishing remain off.

## Repeatable read acceptance

The [read checker](../../../packages/catalogue/src/private-read-check.mjs) verifies an empty pre-publication feed, one to twenty explicitly supplied private detail IDs, disabled report submission and safe `no-store` JSON responses. It repeats the feed read and rejects a catalogue revision change during the check. Its output contains counts and outcomes, without draft IDs, source content or internal errors. It makes no source or AI requests and writes no reports.

The [staging CLI](../../../packages/catalogue/tools/check-staging-reads.mjs), available as `pnpm --filter @skilved/catalogue check:staging-reads`, validates the staging website's environment guards before initializing SDKs. It selects up to twenty existing unapproved draft/review records and runs the checker. It refuses missing drafts, unexpected public entries, unsafe configuration, unavailable reads or exposed details. This is a pre-publication acceptance check, not a general health check after listings become public. It requires an existing keyless authentication setup; it neither installs credentials nor grants permissions.

The real check used short-lived delegated authentication for the existing `catalogue-staging-web` identity. Google's standard verifier checked the ID token's signature, staging audience and verified service-account email. The Firestore client used that identity's existing `datastore.viewer` access. Only the normal HTTP handler's runtime dependency was supplied in memory; responses and database contents were real. This proves delegated reads, rather than attached Cloud Run ADC or the deployed website.

An expiring Token Creator binding was added on that service account only. Token readiness initially received permission denials and later succeeded within the bounded propagation window. Cleanup removed the exact binding; no ingest or reviewer application grant was created. Access tokens were requested for 900 seconds and kept in memory; no downloaded key, provider secret or global ADC configuration was saved. Removing delegation does not recall an already issued token. A separate process confirmed the restored empty service-account IAM policy and all 422 unchanged documents, including origins, decisions, inactive grants, spending and quota cooldowns. There were zero source retrievals, provider calls or cloud data writes.

## Isolated lifecycle evidence

A frozen copy of the 422 staging documents was imported into a fresh `demo-` emulator namespace. Authenticated synthetic reviewer actions on the copied CNH draft exercised the normal store and HTTP handler. Publication without a route check left application actions unavailable. Adding a synthetic exact-destination check required another review before enabling the copied route. Changing the destination immediately restricted the listing, and restoring facts without a new destination check kept application actions unavailable. Withdrawal survived correction; stale restoration and accidental publication were rejected. Explicit restoration followed by closure left application actions unavailable.

These are synthetic reviewer observations on an offline clone. They do not approve the real CNH draft, establish application availability or qualify automatic publication. Original cloned decisions, origins and model accounting stayed unchanged. Two additional synthetic worker integration tests cover the HTTP boundary: automatic publication disappears from discovery at exact check expiry without rewriting its stored projection, and a failed source correction stays restricted before an operator withdrawal survives worker retry.

The four read-check tests and two HTTP lifecycle tests pass separately. All **988 catalogue tests pass** after correcting the test helper for raw freshness-watch documents; the first full run passed 986/988 because two older undated tests decoded those documents as JSON. The helper now reads that collection's actual format before filtering by source. A focused four-test run combines the new lifecycle cases with both affected undated cases. Five staging runtime guard tests also pass separately. Earlier private drill failures came from an unsupported test page size, changed headline/category evidence and a mismatched emulator Auth project. Initial logs and the original test file remain private. No production guard or assertion was weakened.

## Remaining release limits

The real CNH draft remains private at revision 2, with its original employer destination and unverified application availability. No reviewer approval, public projection, worker activation, scheduler, billing link or hosting deployment was added. Gemini remains shadow-only and employer crawling optional/off. Shared cloud totals remain 153 requests, 470,793 known tokens and 72 unknown usages; the retired local snapshot remains unchanged.

Database connectivity, delegated ingestion and delegated private-feed reads are demonstrated. Current application availability, a reviewed staging feed publication, attached hosted identities, hosted website integration, scheduling, recovery and production publication still require their own evidence. The next useful check is the current original application destination and the conditions needed for a reviewed staging listing; an empty private feed alone is not production readiness.
