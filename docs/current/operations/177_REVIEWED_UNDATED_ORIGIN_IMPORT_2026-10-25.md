# Reviewed V1-to-V2 undated origin import

25 October 2026. The catalogue now provides an authenticated history import for a familiar RecentJobs notice moving from V1 to V2 shadow assessment. Import preserves the earliest acquisition saved by the worker, including failed jobs that captured the notice. It does not renew a draft, establish current availability or authorize publication.

## Import boundary

`Catalogue.importUndatedOrigin` requires a verified Firebase identity, the current active `source` role, an audit reason and the exact current source revision. The registered source must be active, permit RecentJobs HTML and apprenticeship ingestion, and explicitly select `shadow_recent_v2` in shadow mode. Source registration and its revision history remain separate authenticated operations.

The strict review object supplies `sourceId`, `sourceRevision`, `url`, archived `html`, `expectedFirstJobId`, `decisionJobId` and `expectedHistoryHash`. The server parses the archived HTML itself. It scans persisted worker captures for the exact notice URL across source IDs, including exception jobs, and compares their deterministic history digest with the reviewed digest. It refuses partial captures, a different first job, another source identity, missing snapshots, changed content hashes or source text, altered publication metadata, and a missing or inconsistent accepted V1 decision. Earlier failed captures cannot be omitted by selecting only successful job IDs.

The first implementation conservatively requires every captured content hash to match the reviewed notice. Histories containing source changes need further review; they are not silently merged. Limits are explicit: at most 1,000 total worker jobs, 50 matching captures and ten distinct snapshots. Exceeding a limit stops the import. A queryable history index is needed before this approach can scale beyond the bounded private runtime.

One transaction creates both immutable origin bindings, an import receipt and the authenticated audit entry. Existing, partial or repeated bindings conflict; concurrent imports cannot overwrite each other. The receipt identifies the reviewed history digest, contributing jobs, V1 decision, actor, time and the limited claim `earliest_persisted_worker_acquisition`. This does not claim the earliest out-of-band source download or human inspection.

The worker uses the same global URL and application-route identity keys. If no origin is bound and it finds another captured job for the notice, it stops before AI with `UNDATED_ORIGIN_IMPORT_REQUIRED`. Two concurrent first captures can both be held for review. A matching authenticated import receipt and both exact origin bindings let a later job resume without deleting the saved hold or failed job. A missing or altered binding cannot release the hold. Imports do not alter accepted drafts, existing expiry timestamps, caches, spent budgets, jobs or model availability records. A subsequent real source fetch and the ordinary V2 timing and final-commit checks remain necessary.

## Operator usage

The backend-only operator CLI accepts `command: "undated-origin-import"`, the strict `review` object above and `reason`. It reads the Firebase ID token from `SKILVED_OPERATOR_TOKEN_FILE`; the command JSON and archived HTML must remain private. There is no public import endpoint or role bootstrap command. Reviewers can inspect `worker_notice_origins` and `worker_origin_imports` through the existing authenticated inspection path.

Compute `expectedHistoryHash` with `undatedHistoryHash` over the reviewed complete matching capture history, retaining actual Firestore document IDs. The import re-reads that history transactionally rather than trusting the caller's list or acquisition timestamp. Missing or conflicting evidence requires investigation, not deletion, a replacement source ID or a cap increase.
