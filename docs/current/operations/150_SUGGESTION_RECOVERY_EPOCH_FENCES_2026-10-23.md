# Suggestion recovery epoch fences

23 October 2026. B06-5c3a adds an independently configured recovery epoch to the [signed-ticket runtime](149_SIGNED_TICKET_HTTP_AND_RUNTIME_2026-10-23.md). Changing this epoch fences restored replay credentials, receipt capabilities and work leases without deleting their stored history. This is local engineering evidence; suggestions remain default disabled and no actual restore, environment change, worker execution or cleanup is performed.

## Configured authority

Enabled suggestion manifests now require one root recoveryEpoch: a new 64-character lowercase hexadecimal identifier from trusted configuration outside the restored database. It must differ from every configured signing/receipt secret. Nested signer recovery settings are refused; the adapter injects the root value into fresh signer and receipt services. The operator queue/review composition uses the same configuration. Public route disablement still returns before manifest/secret reads or SDK initialization.

This epoch is separate from the existing replay-ticket epoch. Ordinary ticket-epoch rotation still preserves receipt capabilities. A deliberate recovery-epoch change invalidates both tickets and receipt access even if the signing key, receipt key ring, ticket epoch and wall clock stay unchanged. Recovery-mode HMAC inputs use separate v2 domains and include the recovery epoch; the bounded s1 ticket wire syntax is unchanged. Receipt records carry their epoch, and missing/different epochs cannot fall back to legacy derivation. Merely changing a stored receipt's epoch cannot preserve its old capability MAC. Admission refuses a missing or mismatched signer/receipt recovery context.

New work leases carry the current recovery epoch. Completion requires that epoch as well as the existing stored ID, generation, owner, source, receipt need and time predicates. A retired lease does not block fresh acquisition under the new context. Only current-epoch receipts can justify new lease work or receive reviewer updates. Withdrawal considers other current-epoch receipts when deciding whether work remains needed. Physical retained/unrevoked accounting still includes old rows: no slot, mapping, receipt or public fact is removed or reset by changing configuration.

Backend constructors retain an explicit legacy composition when the recovery epoch is omitted, for existing internal fixtures/history. That composition cannot derive a recovery-tagged receipt or complete a recovery-tagged lease. Configured public/operator paths require the epoch and have no such fallback. Old binaries or still-running processes with old configuration remain an operational hazard; this code does not remotely revoke their in-memory authority.

## Recovery prerequisite and remaining work

Before an authorized real restore, keep suggestion access/work paused and stop every old runtime, operator and worker process. Retain a fresh, never-reused recovery epoch in trusted configuration outside the backup and apply it coherently to every restarted process before serving restored data. Do not restore that configuration from the same snapshot or reopen an old binary without the fence. Prove the recovery procedure in the actual target environment before exposure. This packet does not execute or independently attest those operational steps; restoring with the same old epoch, reverting configuration, or leaving old processes running is not protected automatically.
