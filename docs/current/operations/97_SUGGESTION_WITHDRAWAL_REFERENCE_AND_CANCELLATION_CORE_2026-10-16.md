## Changed behavior

`SuggestionAdmission.withdraw` charges the existing bounded credential-operation budget shared with status reads, then validates the strict receipt ID/capability before reading shared inventory. Wrong, missing, malformed, cross-receipt, expired and already-revoked credentials receive the same not-found failure. Failed calls and retries consume the committed budget; a rolled-back mutation cannot refund it. Withdrawal needs no new intake, source availability or source permission lookup, so intake-off and paused/missing/corrupt sources do not prevent revocation of valid access.

The transaction reads the validated bounded physical inventory before any writes. It marks only the authorized receipt withdrawn, sets revocation/update time, advances its revision and clears its result IDs, preserving original expiry. Status and create replay then deny that receipt. The minimal strict response contains schema version, the caller's receipt ID and withdrawn status; it has no credentials, URL, results, shared work ID, notes or counts. A lost acknowledgement followed by not-found proves no active access, not physical deletion or why access ended.

Work now distinguishes `receiptCount` (all retained physical receipt documents) from `referenceCount` (unrevoked receipts, including expired receipts until explicit cleanup). Time-dependent work need is calculated separately from unexpired/unrevoked other receipts at the transaction clock. An expired reference therefore cannot keep work needed. Legacy absent reference counts are derived from the actual inventory; explicit inconsistent counts fail closed. New/mutated work persists the derived count. Positive bounded generations default to 1 for earlier work.

Withdrawal decrements one reference without releasing retained capacity or deleting replay history. When another current receipt needs the work, its receipt/credentials, shared outcome and generation stay unchanged. Otherwise work becomes cancelled, clears result IDs and advances generation. Reviewer decisions also advance generation and cannot reopen cancelled work. These are persisted cancellation fences; no running suggestion worker or lease exists in this packet, so no external execution cancellation is claimed.

A fresh key may create separate access and restart cancelled work as pending in a newer generation, after existing source revision/permission/pause and physical-capacity checks. An old receipt/key never revives, and stale reviewer revisions cannot overwrite cancellation. Earlier source-binding drift still fails closed; no implicit source migration is introduced. Independently approved public facts and other submitters' receipts remain intact. All retained receipt/work slots continue to count against capacity until B06-5c cleanup, even when their references are revoked.
