## Configured protocol

POST /api/v1/opportunity-suggestions/tickets accepts the existing strict URL-only JSON request. It accepts neither Authorization nor Idempotency-Key. Current source policy and the shared committed attempt budget govern issuance; a ticket allocates no receipt/work capacity. A normal issuance followed by submission consumes two attempts. The response contains only the signed ticket and its matching expiry. Lost issuance responses can request another ticket; once creation is sent, retain that creation's ticket privately for response-loss recovery.

POST /api/v1/opportunity-suggestions requires the full ticket in Idempotency-Key. Legacy raw keys and internal digests are refused. Syntax/coherence validation is shared with the backend signer; signature, active epoch, URL binding and current validity remain backend checks. Existing status and withdrawal use their own receipt capabilities in Authorization. A ticket is a replay credential, not a public deduplication identifier or a receipt capability.

The enabled trusted manifest requires replayTickets with explicit epoch, secret, notBefore and ttlMs. There are no signing defaults. Its public epoch must differ from the signing key and every configured receipt secret; the signing key must also differ from every receipt secret. Missing or invalid configuration fails before SDK use. Global disablement still returns before reading the manifest. The runtime creates fresh signer/receipt services with the same clock and always selects ticket mode; it has no public legacy fallback. Explicit signer configuration is required even when intake is off and only existing receipt service is needed. This is a configuration migration, not an automatic conversion of legacy histories.

The new tickets route has deliberate Node/dynamic method wrappers and is included in the production boundary inventory. All four suggestion routes remain private/no-store/no-referrer and globally default unavailable. The issuance and create paths share strict body/header/origin/cookie/encoding, read-time and service-time guards. Errors expose fixed codes without input or backend exception text. Intake-off refuses both POST operations while configured capability status/withdrawal remains available. A backend timeout may still commit; it is not cancellation evidence.
