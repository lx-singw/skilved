# Suggestion receipt retention cleanup

23 October 2026. B06-5c3b1 adds backend-only single-receipt cleanup after the [recovery epoch fences](150_SUGGESTION_RECOVERY_EPOCH_FENCES_2026-10-23.md). It can reclaim receipt capacity while retaining work records and their generations. There is no route, CLI command, scheduler, actual configuration change or cleanup of live data. Suggestions remain default disabled.

## Transaction and authority

The primitive requires recovery-mode admission, the same Catalogue/database, and explicit trusted retirement settings: at most eight distinct retired recovery epochs and a boolean legacy-retirement declaration. The current recovery epoch cannot be declared retired. These settings are not accepted in the cleanup command. They represent a prior trusted recovery decision; code cannot attest that old processes were stopped or outside-backup configuration was applied correctly. No such real retirement decision is inferred from these fixtures.

Cleanup uses the existing authenticated source-role mutation and a fixed minimal audit reason. The strict command identifies one receipt and supplies expected receipt, work and admission revisions. Incorrect role, stale revision, malformed input and repeated commands cannot acknowledge deletion. The result contains revision and fixed removal counts, without URL, capability, ticket or private notes.

Before writing, the transaction reconciles the whole bounded physical receipt/work inventory and at most 500 replay bindings. Every retained receipt must have exactly one binding with matching expiry, work/input hash and bounded retention marker. Missing, duplicate, orphaned, inconsistent or malformed history fails closed. Replay JSON has the same 8 KB limit as normal receipt replay reads. No partial cleanup or guessed zero count is accepted.

A current-epoch receipt must be expired or revoked, and its explicit ticket retainUntil must have elapsed. A shorter receipt expiry or earlier withdrawal cannot erase a still-live ticket's denial history. Missing finite windows are not inferred. Different or missing receipt epochs do not automatically establish retirement: old-epoch or undated legacy history requires the corresponding explicit trusted retirement declaration. Once that context is deliberately retired, its invalid replay history can be removed without waiting for the former ticket deadline.

The transaction deletes only the selected receipt and its binding, updates physical receipt and unrevoked-reference counts, and leaves another current receipt's needed work and lease intact. With no remaining current need, it cancels work, clears the lease and advances generation. A zero-receipt work row must be explicitly cancelled with zero references and no lease. It remains a counted private generation anchor, including its URL. Re-admission to the same notice reuses that anchor and advances generation again. Work slots, approved-result replay history, hourly counters and independently sourced public facts are not reclaimed in this packet. A clock rollback observed before callback return aborts queued writes; this is not database-commit-time or transport-cancellation evidence.
