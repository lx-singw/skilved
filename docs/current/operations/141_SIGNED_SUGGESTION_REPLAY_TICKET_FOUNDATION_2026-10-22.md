# Signed suggestion replay-ticket foundation

22 October 2026. B06-5c1 adds a backend-only signer and verifier for expiring, URL-bound replay credentials. It establishes the protocol primitive needed before safely deleting replay history. Existing intake, receipt persistence, HTTP configuration and routes do not use this module yet. Suggestions remain default disabled; no history is deleted or capacity reclaimed.

## Protocol and behavior

The existing intake accepts random 64-hex replay keys without an issuance window. After deleting every mapping, an old unknown key would be indistinguishable from a fresh key. Keeping finite receipt lifetimes alone cannot solve that problem. The selected dependent implementation uses a signed issuance window, with retained replay history until that window ends.

`SuggestionReplayTickets` requires an explicit dedicated 256-bit HMAC key, a 256-bit active epoch identifier, an activation instant, a lifetime from one millisecond to thirty days, and an injected canonical UTC clock. Configuration rejects using the same value for the public epoch and private signing key. There is no default key, database dependency, retained old-epoch fallback, environment configuration or public package export. These synthetic engineering bounds are not an adopted live retention policy.

The bounded ASCII token is `s1.epoch.issuedMillis.expiresMillis.nonce.mac`, at most 230 characters. Epoch, random nonce and MAC each use 64 lowercase hexadecimal characters. Times use canonical decimal milliseconds without signs, exponents or leading zeros. The MAC is HMAC-SHA-256 over the UTF-8 JSON array `["skilved.suggestion.replay-ticket.v1", epoch, issuedMillis, expiresMillis, nonce, canonicalUrl]`, with numeric times. Canonical URL validation reuses the existing conservative suggestion contract. The submitted URL and signing secret are absent from the returned token and verification result.

Verification requires the active epoch, issuance at or after activation and no later than the trusted clock, positive duration within the configured ceiling, a supported calendar instant, an unexpired deadline, and the matching URL-bound MAC. Exact expiry rejects. Tightening the configured lifetime can invalidate previously issued longer tickets. A fixed-format MAC uses `timingSafeEqual`; no whole-request timing claim is made. Invalid tickets, legacy raw keys and changed inputs receive the same fixed `SUGGESTION_NOT_FOUND` error. Invalid trusted configuration or clock fails unavailable, without returning raw exceptions.

The private result contains the epoch, immutable issuance/expiry instants and a domain-separated SHA-256 replay key derived from the complete ticket. That digest is an internal persistence lookup key. It must never become an alternative public credential that bypasses verification. Issuance itself does not create a receipt, deduplicate work, charge admission budgets or fetch a source. Separate issuances receive separate random nonces even for the same notice.

## Verification

Nine new tests and all 37 focused ticket/receipt-crypto/source-policy/config/HTTP/runtime tests pass. A fixed token and replay digest computed with Python's standard-library HMAC/hashlib independently check the wire representation. Cases cover immutable expiry, separate issuance, URL normalization and binding, every altered field, wrong key/domain, legacy/malformed/oversized input, extra fields, final newline, exact activation/expiry, future issuance, policy tightening, minimum/maximum duration, invalid/throwing/rolled-back clocks and calendar overflow.

Reconstructing the verifier with the same epoch accepts an unexpired ticket; changing the external epoch rejects it even with the same key and no database history. This is local verifier evidence, not an observed backup restore or an integrated receipt/lease fence. Frozen code/test hashes match the checked inputs. All 38 contract tests, 90 web tests and the fresh production build, including lint and type checks, pass with no skipped tests. No emulator or browser lifecycle acceptance is inferred from these checks.

## Required dependent work and limits

The next bounded packet must integrate issuance and verification into trusted configuration, contracts, transport and transactional create/replay. Verify the full ticket on each transaction attempt before admitting any receipt or approved-result replay. Clamp receipt and mapping expiry to the ticket deadline; never extend it on retry. Keep response-loss recovery, separate submitter access, existing intake-off status/withdrawal, bounded issuance/attempt budgets and transport-before-runtime guards. Retain legacy history until an explicit fail-closed migration/retirement is verified; this module does not change the currently accepted legacy endpoint protocol.

Cleanup must retain a used ticket's replay binding until its validity ends, even after receipt withdrawal. Only then can removing that history avoid accepting the same expired request as fresh. Atomically reconcile retained and unrevoked references, preserve another submitter's work, cancel unnecessary leases, protect generations across deletion/recreation, and leave independently obtained public facts intact. Both receipt and approved-result replay histories need this treatment. None of those deletion jobs is implemented here.

A database restore can still resurrect an unrevoked receipt or old work generation if its old credentials/configuration remain valid. Before serving restored data, retire the replay epoch in trusted state outside that backup, fence old receipt capabilities and leased work, and test the complete recovery sequence. Merely retaining this helper or restoring the same epoch does not prevent resurrection. Actual independent configuration custody, backup/vendor deletion, purpose/retention notices and staffed operating adoption remain external gates.

No endpoint, scheduler, worker execution, source request, provider call, production setting, deployment or publication is added. B06-5c lifecycle integration, B06-6 browser receipt UI and B06-7 integrated/formal qualification remain open, alongside the earlier source, participant, device and release gates. New source-policy deliveries through `7fc11e3` are credited separately and grant this loop no additional live-call authority.
