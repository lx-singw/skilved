# Shared employer and recruitment-platform relationships

29 October 2026 (SAST). Employer/ATS route trust can now be stored independently of a RecentJobs publisher policy. A worker resolves the applicable current relationships by the application destination, pins their revisions for its attempt and rechecks them before consequential work. Once a relationship is qualified, future vacancies do not require another employer list, source registration or grant.

This builds on [publisher discovery](196_RESUMABLE_PUBLISHER_DISCOVERY_2026-10-29.md) and [original-notice corroboration](197_ORIGINAL_NOTICE_CORROBORATION_2026-10-29.md). It implements trust separation within the [autonomous system sequence](../engineering/17_AUTONOMOUS_OPPORTUNITY_SYSTEM.md). Automatic discovery and corroboration of previously unknown employer authority remain open; the registry is not an AI-generated whitelist or proof that an arbitrary website is official.

## Authority records and controls

`m0_employer_relationships` stores the current relationship. Each record has a stable ID, optimistic revision, qualified/revoked state, supported categories, review/expiry times and an issuer route containing name/aliases, exact host, tenant/path prefix, exact email recipients where stated and relationship evidence. `m0_employer_relationship_versions` retains immutable revisions. One relationship can serve several publisher policies and many vacancy URLs; it is not a vacancy record or an assertion that a specific intake is open.

The existing authenticated operator API now provides `registerEmployerRelationship`. It requires the source role, an expected revision and an audit reason, like source registration. The private operator CLI exposes `employer-relationship` with `relationship`, `expected` and `reason`. There is no role/bootstrap command, public write route, worker trust-creation capability or model-output-to-authority write path. Current qualification cannot have a future review or elapsed expiry. Revocation remains possible after an older qualification expires. Concurrent revisions conflict rather than overwriting each other.

Host/recipient lookup keys are generated by code and stored beside the JSON record. Reads check that index metadata agrees with the strict authority record. A corrupt or inconsistent index cannot silently expand its scope. Relationship evidence remains a reviewed trust input under the source operator's authority; the implementation does not independently validate a free-text evidence reference or infer a corporate domain from its spelling.

## Publisher policy and worker binding

A source opts in with `automation.issuerRegistry: "shadow_v1"`, `originalVerification: "shadow_v1"` and an empty `issuers` array. No employer IDs are embedded in the publisher configuration. Its category, source permission, source ID/revision, URLs, cadence, request pacing, acquisition flag, model-call budget and grant remain separate controls. Existing inline-issuer sources retain their behavior.

Registry mode requires the existing original-notice shadow lane and dated-notice policy; inline trust fallback and automatic mode are rejected. Disabled mode and pause remain available. Employer crawling is still optional; turning it off still prevents employer requests and holds this verification lane without model work. Programme extraction remains blocked by the original-notice lane's existing guard. Shared trust does not qualify a source's reuse permissions, an email submission method or a different ATS capability.

The worker performs an indexed lookup by exact host or email recipient, then checks current state, category, review/expiry window and path/recipient scope. Path matching preserves tenant boundaries; a similarly prefixed tenant or another recipient on the same domain is not inferred. The first bounded implementation holds if more than 30 records share a lookup key. It does not scan every employer or silently truncate authority. A more selective tenant index is needed before supporting very large shared ATS hosts.

Each detail attempt writes an immutable private `m0_worker_issuer_resolutions` receipt linking source/revision, job/attempt, publisher snapshot, selected relationship IDs/revisions/content hashes and exclusions such as expiry, revocation, category or path mismatch. Original-notice receipts, worker exceptions and successful private decisions link this receipt. Authenticated reviewers can inspect/list the new private state; no authority record or trust receipt is added to public projections.

Only runtime-validated relationships populate the worker's issuer context. This is never saved back as the publisher's inline issuer list. An empty/missing context cannot fall back to publisher-local trust. Unknown, expired or revoked origins remain held without an employer fetch or AI call; no new official URL or permission is invented.

## Revocation, caches and accounting

The worker re-reads pinned relationships at its existing claim checks before paced fetches, model reservations, answer/cache use and draft completion. Revision/content changes, removal and expiry prevent further positive use and produce a persisted trust exception. An issuer revocation is not relabelled as employer-site unavailability or vacancy closure. The same revocation affects subsequent attempts under every registry-enabled publisher that would use that relationship.

Already dispatched AI calls still receive their usage/result accounting if issuer trust changes while they are in flight. Their answers cannot proceed into cache use, validation or drafting. Existing machine grant, source, lease and quota-authority fences still apply to accounting; this change is specifically about issuer authority, not an unconditional accounting bypass.

New attempts perform a fresh lookup instead of inheriting an older attempt's trust. The cache context includes registry version and relationship revision/content bindings, so an updated authority cannot reuse an older assessment as if it were current. Old caches, receipts, versions and spend are preserved; usage is not refunded and a new relationship is not a new source allowance.

## Migration and compatibility

A publisher can transition through the existing source-registration API using the same ID, revision plus one, the registry flag and empty inline issuers after its required relationships exist. Do not clone a source or rename it to acquire budget. Existing source versions, snapshot citations, record IDs and grants remain valid history. This sprint supplies and tests that path but performs no live source migration or relationship registration.

Local checkpoint export discovers the new collections automatically. The older historical staging-import manifest is not extended to migrate active registry authority. Human reviewer publication controls remain separate and unchanged; the new automated lane is still shadow-only. Supporting another publisher adapter is also separate from demonstrating shared trust across two independent RecentJobs test policies.

## Verification

Ten authored emulator cases cover two publisher policies and several tenants using the same relationships, unknown origins, source configuration fences, role/revision checks, immutable history, concurrent revocation, revocation during acquisition and AI, expiry during validation, current-context cache invalidation, migration without identity/spend reset, corrupt indexes, capacity overflow, category scope, exact recipients and future/expired qualification. Model calls and identity verification are simulated; these tests do not establish real employer authority or measured production accuracy.

The in-flight revocation case retains the received usage for its sole dispatched model call and blocks validation/drafting. The migration case retains the same source, worker grant, record ID and old source version while accumulated spending advances from five historic calls to nine after two legitimate two-call assessments. No allowance is reset.

The affected serial emulator run passes **243/243 tests**, including all ten registry cases plus original-notice resolution, publisher discovery, legacy worker/policy, source registration/publication, fetch safety and publication previews. Contract build/typecheck and all **five staging runtime guard tests** pass. Operator help exposes the new command without initializing a runtime or reading credentials. The full catalogue suite is not rerun; the earlier intermittent suggestion-route failure remains open.

The rebuilt local worker image runs as `node` and passes network-disabled checks for shared registry binding, strict index validation, no inline fallback, changed-authority rejection and the shadow-only source policy. Disabled launcher activation remains rejected, and no image is deployed. Changed-document local links and Git whitespace checks pass. Private logs and receipts remain in ignored `.artifacts/groq/issuer-registry-2026-10-29/`.
