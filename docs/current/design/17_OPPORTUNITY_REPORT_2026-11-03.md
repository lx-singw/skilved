# Opportunity issue reporting

Implemented: 3 November 2026.

The opportunity’s evidence section now opens a report workbench with four native radio tiles instead of a generic select. Each concern has its own prompt: information to clarify, a possibly closed intake, a suspicious destination or payment request, and another issue. The closed-intake prompt distinguishes an inaccessible site from established closure. Suspicious-destination guidance asks for information already held, without prompting another visit. The existing private-review and personal-information guidance remains.

The controlled description has a 1,500-character bound and a counter that does not announce every keystroke. Its draft remains in the current page’s component state; there is no draft storage or cross-device recovery. Leaving or reloading can lose it. Sending disables the issue group and description, exposes busy state and blocks a duplicate submission synchronously. Failed or unconfirmed attempts retain the selected concern and description. Changing opportunity identity remounts the report; disposal aborts its request and prevents a late response from updating the departed form.

Only a validated HTTP 202 JSON acknowledgement containing exactly status: received clears the form and displays receipt confirmation. Receipt is distinguished from a verified issue or resolved review, an application submission and a change to saved progress. The endpoint supplies no tracking reference, and the confirmation invents none. A user may return to the evidence or explicitly start a different blank report, which focuses the first issue choice and sends nothing by itself. Error and confirmation panels receive focus; the concern group, legend, labels and ordinary native disclosure remain keyboard accessible.

The extracted transport sends one same-origin JSON POST containing only opportunityId, kind and trimmed text. Identifier and description validation match the existing report contract. Requests omit cookies, cache and referrer and reject redirects. A single ten-second overall deadline bounds both fetching and acknowledgement reading, including implementations that ignore cancellation. Acknowledgements are limited to 2 KiB, decoded strictly and checked before confirmation. Invalid JSON, extra fields, incomplete or oversized bodies, redirects and network uncertainty cannot become success. HTTP validation rejection, rate limiting, unavailability and unconfirmed receipt have distinct copy; raw response errors are not rendered. There is no automatic retry or new idempotency protocol; an explicit retry after uncertain receipt can duplicate an earlier arrival, which the copy explains.
